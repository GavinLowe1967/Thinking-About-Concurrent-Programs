\section{Signalling Using Semaphores}

Recall, that a semaphore that is used to enforce mutual exclusion is initially
\emph{up}.  A thread that enters the critical region does a \SCALA{down}, to
block other threads from entering.  When it leaves the critical region it does
an \SCALA{up}, to allow other threads to proceed.

By contrast a \emph{signalling semaphore} is initially \emph{down}.  A thread
can send a signal by performing an \SCALA{up}.  A thread waits for a signal by
performing a \SCALA{down}.
\begin{scala}
  private val signal = new Semaphore(false)
  def signaller = thread{ ...; signal.up(); ... }
  def waiter = thread{ ...; signal.down(); ... }
\end{scala}  
Alternatively, the signalling semaphore can be created using
\begin{scala}
  private val signal = new SignallingSemaphore
\end{scala}
via the definition
\begin{scala}
  class SignallingSemaphore extends Semaphore(false)
\end{scala}
%
The \SCALA{waiter} cannot proceed before the signal is sent (but the
\SCALA{signaller} can proceed before the signal is received).
Note that the signal is received by only one other thread.  

I think of a signalling semaphore as rather like how one might send a signal
using a flag.  The flag is put \emph{up} to send the signal.  When the signal
is received, the flag is put \emph{down}. 

%% Note also that if the |signaller| performs the signal before the |waiter|
%% is ready, the signal is not lost.

Semaphores and conditions are similar, in that each provides a signalling
mechanism.
%
The main difference is that a semaphore has a state: it is either \emph{up} or
\emph{down}.  This means that if an |up| operation is performed before a
thread is waiting (when the semaphore is in the \emph{down} state), then the
signal is not lost (the semaphore moves to the \emph{up} state).
%
By contrast, if a signal is performed on a condition when
no thread is waiting, then the signal is lost: in such cases, it is often
appropriate to use the condition in combination with a boolean variable. 

Two threads can synchronise using a pair of signalling semaphores: each
signals to the other when it reaches the synchronisation point; neither
proceeds until it has received the signal from the other.
\begin{scala}
  val signal1 = new SignallingSemaphore; val signal2 = new SignallingSemaphore
  def t1 = thread{ ...; signal1.up(); signal2.down(); ... }
  def t2 = thread{ ...; signal2.up(); signal1.down(); ... }
\end{scala}


The above code works fine if the threads use the semaphores to synchronise
just once.  However, it can go wrong if the threads use the same semaphores to
synchronise multiple times.
%
\begin{scala}
  def t1 = thread{ for(i <- 1 to 2){ ...; signal1.up(); signal2.down(); ... } }
  def t2 = thread{ for(i <- 1 to 2){ ...; signal2.up(); signal1.down(); ... } }
\end{scala}
%
%% Consider an execution of the above where each thread should executes the loop
%% precisely twice.
The following sequence of events is possible, where the
subscripts represent the iteration number.
\[
\begin{align}
\sm{signal1.up}_1,\; \sm{signal2.up}_1,\; \sm{signal2.down}_1,\;
   \sm{signal1.up}_2.
\end{align}
\]
Here, thread~|t2| is suspended after performing its first signal, so that |t1|
performs its second signal \emph{before} |t2| consumes the first signal.  With
our implementation of semaphores, the precondition of |up| is not satisfied,
and an exception is thrown.  If we had allowed an |up| when the semaphore is
already up (and made it a no-op), the second signal on |t1| would be lost.
The execution would have continued something like:
\[
\begin{align}
%\sm{signal1.up}_1,\; \sm{signal2.up}_1,\; \sm{signal2.down}_1,\;
%   \sm{signal1.up}_2, \\
\ldots,\; \sm{signal1.down}_1,\; \sm{signal2.up}_2,\; \sm{signal2.down}_2.
\end{align}
\]
Subsequently, |t1| terminates, but |t2| is stuck waiting for a second signal
on |signal1|.  It would be difficult to track down the cause of this problem. 

A solution is to reverse the order of events in one of the threads.
\begin{scala}
  def t1 = thread{ for(...){ ...; signal1.up(); signal2.down(); ... } }
  def t2 = thread{ for(...){ ...; signal1.down(); signal2.up(); ... } }
\end{scala}
%
We can reason as follows (using the ``happens before'' relation $\prec$).
\[
\begin{array}{rcl@{\qquad}l}
\sm{signal1.up}_1 & \prec & \sm{signal1.down}_1 & 
  \mbox{(signal on {\scalashape signal1})} \\
 & \prec & \sm{signal2.up}_1 & \mbox{(program order for \SCALA{t2})} \\
 & \prec & \sm{signal2.down}_1 & \mbox{(signal on {\scalashape signal2})} \\
 & \prec & \sm{signal1.up}_2 & \mbox{(program order for \SCALA{t1})} \\
 & \prec & \ldots
\end{array}
\]
In particular, the events happen in the expected order, and neither thread
completes the synchronisation on the $n$th iteration before the other thread
has signalled on that iteration.
%
The precondition of |up| is satisfied since $\sm{signal1.down}_n \prec
\sm{signal1.up}_{n+1}$ and $\sm{signal2.down}_n \prec \sm{signal2.up}_{n+1}$,
for each~$n$.

\section{A Partial Queue Using Semaphores}

To illustrate the technique of signalling using semaphores, we will implement
a partial queue.   The implementation is in
Figure~\ref{fig:SemaphorePartialQueue}. 
%
If a |dequeue| finds that the queue is empty, it will wait for a signal on a
signalling semaphore |nonEmptyS|.  When a subsequent |enqueue| signals on
this semaphore, it will indicate that the queue is now non-empty (in fact,
that the queue contains precisely one element), and the |dequeue| can proceed.
%
In addition, we have to protect the shared variables from  race conditions.  We
use a |MutexSemaphore| |mutex| for this. 
%
When an |enqueue| finishes, it will either (1)~signal on |nonEmptyS| to a
waiting |dequeue| if there is one (and leave the mutex down), or (2)~lift the
mutex.  We record the number of waiting |dequeue|s to support this.

%%%%%

\begin{figure}
\begin{scala}
class SemaphorePartialQueue[T] extends PartialQueue[T]{
  /** The queue itself. */
  private val queue = new Queue[T]

  /** Number of waiting dequeues. */
  private var waitingDequeues = 0

  /** Semaphore to provide mutual exclusion. */
  private val mutex = new MutexSemaphore

  /** Semaphore on which a £dequeue£ waits until the queue is non£-£empty. */
  private val nonEmptyS = new SignallingSemaphore

  /** Enqueue x. */
  def enqueue(x: T) = {
    mutex.down()
    queue.enqueue(x)
    if(waitingDequeues > 0) nonEmptyS.up() // Pass the baton to a £dequeue£.
    else mutex.up()
  }

  /** Dequeue a value. */
  def dequeue(): T = {
    mutex.down()
    if(queue.isEmpty){  // Thread has to wait.
      waitingDequeues += 1; mutex.up()
      nonEmptyS.down() // Wait for signal.
      assert(queue.length == 1)
      waitingDequeues -= 1
    }
    val result = queue.dequeue(); mutex.up(); result
  }
}
\end{scala}
\caption{A partial queue implemented using semaphores.}
\label{fig:SemaphorePartialQueue}
\end{figure}


%%%%%


The technique used by |enqueue| is known as \emph{passing the baton}.  The
|enqueue| decides what sort of operation should run next---either a waiting
|dequeue| or a new operation---and ``passes it the baton'' by lifting the
appropriate semaphore.  This is a very useful technique.  Often the current
thread is in the best position to decide which thread can run next.  The
technique allows us to choreograph the threads, so that they perform steps in
an appropriate order: enforcing a rigid order makes the implementation easier
to understand.  We will use the technique again in later examples.

There are two important things to remember when using the technique of passing
the baton.
%
\begin{enumerate}
\item
When a thread passes the baton to a thread waiting on a signalling semaphore,
it leaves the mutex semaphore down: the latter thread takes over the rights
implied by possession of the mutex.  It the signalling thread were to lift the
mutex, it would allow some third thread to obtain it, therefore invalidating
the intended logic.

\item
By contrast, the waiting thread should lift the mutex before waiting:
otherwise the system will deadlock.
\end{enumerate}

\begin{instruction}
Study the details of the implementation of the partial queue.  Make sure you
understand the rationale for each semaphore operation.
\end{instruction}

\section{Barrier Synchronisation}

We now use semaphores to implement a barrier synchronisation that can be used
to synchronise $\sm n > 1$ threads.  The implementation again uses the
technique of passing the baton.  

The implementation is in Figure~\ref{fig:SemaphoreBarrier}.  It records the
number of threads currently waiting in a variable \SCALA{waiting}.  This is
protected by a mutex semaphore.


\begin{figure}[htbp]
\begin{scala}
class SemaphoreBarrier(n: Int) extends tacp.dataParallel.BarrierT{
  require(n > 1)
  /** Number of threads currently waiting. */
  private var waiting = 0 
  /** Semaphore to signal to waiting threads. */
  private val waitSem = new SignallingSemaphore()
  /** Semaphore for mutual exclusion. */
  private val mutex = new MutexSemaphore()

  def sync(me: Int) = {
    mutex.down()
    if(waiting == n-1) waitSem.up()
    else{ 
      waiting += 1; mutex.up(); waitSem.down() // Wait until woken.
      waiting -= 1
      if(waiting==0) mutex.up() else waitSem.up() // Pass the baton.
    }
  }
}
\end{scala}
\caption{An implementation of a barrier synchronisation object using
  sem\-a\-phores.}
\label{fig:SemaphoreBarrier}
\end{figure}

The implementation uses a signalling semaphore \SCALA{waitSem} to block the
first $\sm n-1$ threads.  The $\sm n$th thread signals on this semaphore to
unblock another thread, i.e.~passes it the baton.  That thread passes the
baton to another waiting thread (assuming $\sm n \ge 3$), and so on.  The
final thread to be awoken raises the mutex, to pass the baton to a thread on
the next round.

%% %%%%%
%% \begin{slide}
%% \heading{Barrier synchronization}

%% \begin{itemize}
%% \item
%% The first $n-1$ threads  end up blocked on \SCALA{waitSem.down};

%% \item The $n$th thread performs \SCALA{waitSem.up}, to pass the baton to
%% another thread, and returns;

%% \item In turn, $n-2$ threads are woken, decrement \SCALA{waiting}, and wake up
%% the next thread;

%% \item The final thread to be woken, performs \SCALA{mutex.up} to allow the
%% following round of synchronisation to proceed.
%% \end{itemize}

Note that after the $\sm n$th thread has called |sync|, no other thread can
obtain the mutex until the last thread exits, since \SCALA{mutex} remains
down.  This prevents different rounds from interfering.

\begin{instruction}
Study the details of the implementation.  Persuade yourself that the semaphore
operations must occur in the order described.
\end{instruction}
