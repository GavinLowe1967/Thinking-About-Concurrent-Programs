\section{Waiting and Signalling Using JVM Monitors}

We now consider the second aspect of JVM monitors, namely the wait/signal
mechanism.  If |o| is a reference object, then it has the following
operations, each of which can be performed only inside a |synchronized| block
on~|o|:
\begin{itemize}
\item |o.wait()|: suspend, giving up the lock on~|o|; wait for a signal, and
  then re-acquire the lock;

\item |o.notify()| : signal to a thread waiting on~|o|, if there is
  one (if there is no thread waiting, the operation has no effect);

\item |o.notifyAll()|: signal to all threads waiting on~|o|. 
\end{itemize}
%
Each operation should be performed while holding the lock on~|o|, i.e.~from
inside a |synchronized| block on~|o|.  When a thread signals, it keeps the
lock: the thread that receives the signal must wait for the signaller to
release the lock, and then needs to compete with other threads to re-acquire
the lock.  This also ensures memory consistency. 

The operation |wait()| is shorthand for |this.wait()|, i.e.~where the thread
waits on the current object.  The operations |notify()| and |notifyAll()| are
similar.  Thus these forms go together with |synchronized| blocks on the
current object.

% \section{Implementing a Lock}

We illustrate the technique by using a JVM monitor to implement a simple lock.
The implementation in Figure~\ref{fig:jvmMonitorLock} uses a boolean variable
|locked| to record whether a thread currently holds the lock.  The |acquire|
operation waits until |locked| is |false|, and sets |locked| to |true|.  The
|release| operation sets |locked| to |false|, and signals to a waiting thread
in |acquire|.

%%%%%

\begin{figure}
\begin{scala} 
class Lock{
  /** Does a thread currently hold the lock? */
  private var locked = false

  /** Acquire the lock. */
  def acquire() = synchronized{
    while(locked) wait() // Wait for current thread to release the lock. 
    locked = true
  }

  /** Release the lock.*/
  def release() = synchronized{
    locked = false
    notify() // Signal to an £acquire£.
  }
}
\end{scala}
\caption{An implementation of a lock using a JVM monitor.}
\label{fig:jvmMonitorLock}
\end{figure}

%%%%%

Note that there are two levels of locking going on in this example.  Each
operation uses a |synchronized| block, which provides a lock on the |Lock|
object, to protect the shared variable |locked|, and to ensure that the
threads execute in a one-at-a-time order.  However, the |Lock| object provides
a lock that can be used by client code.  It is reasonable to suppose that each
thread that acquires the |Lock| will hold it for a reasonable amount of time,
longer that the time a thread spends running in the |acquire| or |release|
operations.  Thus the |synchronized| blocks act as a short-term lock, but each
|Lock| object acts as a longer term lock.

When the |acquire| operation receives a signal, it has to recheck whether
|locked| is true, because it is possible that some other thread has called
|acquire| in the meantime, and set |locked| to |true|.  This is similar to
what we had to do in several examples that use |Condition|s.

However, there is another reason why the |acquire| operation needs to perform
this check, which would hold even if there were no other thread that could
attempt |acquire|.  Sometimes a call of |wait| wakes up even if no other
thread has signalled!  This is known as a \emph{spurious wakeup}.  I consider
this a bug (apparently it is caused by a similar feature in operating system
threading implementations; but it is a feature that the JVM fails to deal
with).  Nevertheless, we have to deal with it.  That means that whenever a
call of |wait| wakes up, the thread should recheck the relevant condition, in
case it has received a spurious wakeup.

\end{instruction}

One way to test this implementation is to have a shared counter, and to
arrange for threads to increment or decrement the counter, protected by
a |Lock|; at the end, we can check that the counter holds the expected value.

Alternatively, we can test the lock for linearizability, by considering a lock
to be a datatype with two states, {locked} and {unlocked}.  We can arrange for
threads to repeatedly acquire and release the lock.  Then we can test for
linearizability, taking the sequential specification object to be a |Boolean|,
with |true| representing that the lock is held by a thread, and with
operations defined as follows.
%
%\begin{mysamepage}
\begin{scala}
  type SeqLock = Boolean
  def seqAcquire(held: SeqLock): (Unit, SeqLock) = { require(!held); ((), true) }
  def seqRelease(held: SeqLock): (Unit, SeqLock) = { assert(held); ((), false) }
\end{scala}
%\end{mysamepage}
%
(We use |assert|, rather than |require|, in |seqRelease|, because the property
failing would represent an error in the testing system, rather than an attempt
to linearize an operation at the wrong point: we expect a thread to call
|release| only when it holds the lock.  If the assertion were to fail, the
linearizability tester would throw an exception.)

Note that, unlike SCL |Lock|s, this implementation of a lock is not
re-entrant: a thread that holds the lock cannot acquire it for a second time.
To do so, the implementation would have to record which thread currently holds
the lock (the SCL implementation stores the relevant |java.lang.Thread|
object), and how many times that thread holds the lock.

\section{Conditions}

Building on the previous section, we now implement a mechanism similar to SCL
|Condition|s.  The implementation is in Figure~\ref{fig:JVM-Condition}.  Each
|Condition| is associated with a |Lock| |lock|, which is provided as a
parameter of the class.  Each of the operations on the |Condition| should be
called while holding |lock|. 

%%%%%

\begin{figure}
\begin{scala}
class Condition(lock: Lock){
  /** An object that allows a single thread to wait to receive a signal. */
  private class Signal{
    /** Has there been a signal? */
    private var done = false

    /** Wait for a signal. */
    def await() = synchronized{ while(!done) wait() }

    /** Signal to the waiting thread. */
    def signal() = synchronized{ done = true; notify() }
  }

  /** Queue of waiting £Signal£ objects, protected by £lock£. */
  private val queue = new scala.collection.mutable.Queue[Signal]

  /** Wait for a signal.  Precondition: this thread holds £lock£. */
  def await(): Unit = {
    val mySignal = new Signal; queue.enqueue(mySignal); lock.release()
    mySignal.await(); lock.acquire()
  }

  /** Signal to a waiting thread.  Precondition: this thread holds £lock£. */
  def signal() = {
    if(queue.nonEmpty){ val sig = queue.dequeue(); sig.signal() }
  }

  /** Signal to all waiting threads.  Precondition: this thread holds £lock£. */
  def signalAll() = {
    while(queue.nonEmpty){ val sig = queue.dequeue(); sig.signal() }
  }
}

class Lock{
  // ... As earlier.

  /** Get a £Condition£ associated with this. */
  def newCondition = new Condition(this)
}
\end{scala}
\caption{A {\scalashape Condition} implemented using a JVM monitor.}
\label{fig:JVM-Condition}
\end{figure}

%%%%%

The implementation is based around an inner class |Signal|, which allows a
single thread to wait to receive a signal.  Each |Signal| object acts as a
monitor: the uses of |synchronized|, |wait| and |notify| are on that |Signal|
object, and are independent of |lock|.  The |Signal| contains a boolean
variable |done| that indicates whether a signal has been sent on the object.
A waiting thread simply waits for |done| to become true.  A signalling thread
sets |done| to true, and notifies the waiting thread.

Each |Condition| object encapsulates a queue of |Signal| objects, one for each
thread that is currently waiting.  Each operation on the queue is done while
holding |lock|, to avoid races.

A thread performs |await| by creating a new |Signal| and adding it to the
queue.  It then releases |lock| (to allow other threads to run), and waits on
the |Signal|.  Finally, it reacquires |lock|.  The |signal| operation simply
signals on the first |Signal| object in the queue, if there is one.  The
|signalAll| operation signals on all the |Signal| objects in the queue.

Finally, we add an operation |newCondition| to |Lock|, to obtain a new
|Condition| associated with that |Lock|.

The |done| variable in each |Signal| serves two purposes.  First, it deals
with spurious wakeups: if a thread does perform a spurious wakeup, when there
was no signal, then it will find $\sm{done} = \sm{false}$, and so wait again.
Second, it protects against a possible race.  Suppose a thread~$t$ in |await|
enqueues its |Signal|, releases |lock|, but is then suspended.  Then it is
possible that another thread sends a signal before $t$ is waiting on the
|Signal|.  But in this case, when $t$ does resume, it will find $\sm{done} =
\sm{true}$, and immediately continue.

\begin{instruction}
Study the details of the implementation.  Make sure you understand the
different orders in which threads can wait or signal on the |Signal|, and
acquire or release the |Lock|. 
\end{instruction}

The use of a queue gives an additional benefit: threads receive signals
in the same order in which they start to wait (although they may reacquire the
lock in a different order).  This provides a degree of fairness. 

Perhaps the easiest way to test this implementation is to edit one of the
examples from Chapter~\ref{chap:conditions} to use this implementation of
locks and conditions in place of the SCL implementation, and then to check
that it still passes its tests.

\section{Partial Queues}

We now use a JVM monitor to implement a partial queue; see
Figure~\ref{fig:partial-queue-JVM-monitor}.  The |dequeue| operation has to
wait if the queue is empty.  An |enqueue| operation performs a |notify|, to
wake up a waiting |dequeue|.
%
As with the implementation using a |Condition| in
Figure~\ref{fig:MonitorPartialQueue}, a waiting |dequeue| needs to recheck
whether the queue is empty when it receives a signal, for two reasons: it is
possible that some other thread has performed a |dequeue| in the meantime and
emptied the queue; and it needs to guard aganist a spurious wakeup.

%%%%%

\begin{figure}
\begin{scala}
import scala.collection.mutable.Queue

class JVMMonitorPartialQueue[T] extends PartialQueue[T]{
  /** The current state of the queue. */
  private val queue = new Queue[T]

  /** Enqueue £x£. */
  def enqueue(x: T) = synchronized{ 
    queue.enqueue(x) 
    notify() // Signal to a waiting £dequeue£.
  }

  /** Try to dequeue, blocking while the queue is empty.  */
  def dequeue(): T = synchronized{ 
    while(queue.isEmpty) wait() // Wait for a value.
    queue.dequeue() 
  }
}
\end{scala}
\caption{A partial queue implemented using a JVM monitor.}
\label{fig:partial-queue-JVM-monitor}
\end{figure}

The implementation of an unbounded partial queue is fairly straightforward,
because there is a single point in the code where a thread can wait.  The same
is true of the implementation of a lock in the previous section.  However,
things are harder when threads can wait in multiple different places.  SCL
monitors allow signals to be targeted to the correct place, by using a
different |Condition| for each.  However, there is no similar way to target
signals in a JVM monitor.  If there are threads waiting in multiple places,
when there is a signal, it will be nondeterministic where the signal is
received, so it might well be received in the wrong place!

In such circumstances it is necessary to use |notifyAll|.  This means that the
signal will be received by all threads, so it will reach the right place if
there is a thread waiting there.  However, threads waiting in other places
should identify that the signal was not intended for them, and wait again.
And likewise, if there are multiple threads waiting at the place to which the
signal was intended, the first to obtain the lock can continue (if not
preempted by another thread), but the remainder should normally wait again.

This is illustrated in Figure~\ref{fig:bounded-partial-queue-JVM-monitor}, to
implement a bounded partial queue.  Again, a |dequeue| has to wait when the
queue is empty; in addition, an |enqueue| has to wait when the queue is full.
An |enqueue| signals to a waiting |dequeue|; but it has to perform
|notifyAll()|, in case there are both |enqueue|s and |dequeue|s waiting.
Likewise, a |dequeue| signals to a waiting |enqueue|, but again has to perform
|notifyAll()|.  (In fact, when we use |notifyAll|, we can't have enqueues and
dequeues waiting simultaneously, because the waiting conditions are disjoint;
but we could if we used |notify|.)

%%%%%

\begin{figure}
\begin{scala}
class JVMMonitorBoundedPartialQueue[T](bound: Int) extends PartialQueue[T]{
  require(bound > 0)

  /** The current state of the queue. */
  private val queue = new Queue[T]

  /** Enqueue £x£. */
  def enqueue(x: T) = synchronized{ 
    while(queue.length == bound) wait() // Wait for a space (1).
    queue.enqueue(x)
    notifyAll() // Signal to a waiting dequeue at (2).
  }

  /** Try to dequeue, blocking while the queue is empty.  */
  def dequeue(): T = synchronized{ 
    while(queue.isEmpty) wait() // Wait for a value (2).
    val result = queue.dequeue() 
    notifyAll() // Signal to a waiting enqueue at (1).
    result
  }
}
\end{scala}
\caption{A bounded partial queue implemented using a JVM monitor.}
\label{fig:bounded-partial-queue-JVM-monitor}
\end{figure}

Having to use |notifyAll| is a disadvantage of JVM monitors.  It will
typically mean that several threads are woken up, only for most of them to
have to wait again.  Scheduling and descheduling threads are
quite expensive operations, so this adds a fairly significant overhead.  In
such cases, it is probably better to use |Condition|s, which allow targeted
signalling.
