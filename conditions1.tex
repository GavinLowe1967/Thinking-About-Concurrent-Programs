In the previous chapter, we saw how we could use a lock to provide mutual
exclusion.  This technique allows us to implement many concurrent objects,
including total concurrent datatypes.  However, it is not enough to implement
a partial concurrent datatype, where a thread might have to wait until some
condition becomes true, or a synchronisation object, where a thread might have
to wait for another thread with which to synchronise. 

For example, consider a partial queue.  Here, if a thread attempts to dequeue
when the queue is empty, it should wait until the queue becomes nonempty.
During this time, we would like the thread to \emph{suspend}, and so stop
using computational resources.  When another thread does enqueue a value, it
should signal to the suspended thread, so that it can resume.  

In order to achieve this, we need a wait/signal mechanism.  In SCL, this is
provided by \emph{condition objects}\index{condition}, of type
|Condition|\SCLIndex{Condition}.  If |lock| is a
|Lock|\SCLIndex{Lock}, then\SCLIndex{newCondition}
\begin{scala}
  lock.newCondition
\end{scala}
creates a new |Condition| object associated with |lock|.  
Each condition has operations as follows:
%
\begin{itemize}
\item |await()|\SCLIndex{await}: suspend, giving up the lock; wait for a
signal on the condition, and then re-acquire the lock;

\item |signal()|\SCLIndex{signal}: signal to a thread waiting on this
condition, if there is one (if there is no thread waiting, the operation has
  no effect);

\item |signalAll()|\SCLIndex{signalAll}: signal to all threads waiting on this
  condition.
\end{itemize}
%
Each operation should be performed while holding the related |Lock|.  When a
thread signals, it keeps the lock: the thread that receives the signal must
wait for the signaller to release the lock, and then needs to compete with
other threads to re-acquire the lock. 

The implementation of conditions is fair: when a thread signals, that
signal is received by the thread that has been waiting longest. 

There is also a timed version of the |await| operation.  The operation
|awaitNanos(nanos)|\SCLIndex{awaitNanos}, where |nanos| is a |Long|, waits for
at most |nanos|~ns.  It returns a boolean that indicates if a signal was
received.  This operation can be used to implement timeouts; but we will not
use it subsequently in this book.

In Figure~\ref{fig:thread-states} we gave a diagram describing different
states that a thread can be in.  Figure~\ref{fig:thread-states-2} augments
this to include consideration of locks and conditions.  The ``Blocked'' state
corresponds to a thread blocking to obtain a lock, whereas the state ``IO
Blocked'' corresponds to a thread blocking for input or output.  The
``Waiting'' state corresponds to a thread that is performing |await()|; note
that when it receives a signal, it becomes blocked, and has to wait to obtain
the lock.

Recall from the previous chapter that when a thread releases a |Lock|,
it \emph{publishes}\index{publish} the values in the cache, making them
available to other threads, and when a thread aquires a |Lock|, it
\emph{subscribes}\index{subscribe} to all variables published by other threads
on the same |Lock|.  The same is true when a thread releases a |Lock| at the
start of an |await|, and reacquires a lock after an |await|.  Thus correct use
of these operations ensures cache consistency. 

The rest of this chapter illustrates the use of conditions in
examples.

\section{Partial Queues}

Figure~\ref{fig:MonitorPartialQueue} uses conditions to implement a
partial queue.  %% (The helper trait |PartialQueue1| gives a default no-op
%% implementation of the |shutdown| operation.)  
Here, a |Lock| is used for
mutual exclusion.  In addition, a |Condition| |notEmpty| is used to allow a
|dequeue| that cannot proceed---because the queue is empty---to wait; this
releases the lock.  A thread that performs an |enqueue| signals on |notEmpty|
to indicate that the queue is now not empty.  The waiting thread that receives
the signal  has to wait to reacquire the lock, which is done as part of
the |await| operation.  It then needs to recheck whether the queue is empty:
it is possible that another thread performed a |dequeue|, after this thread
received the signal but before it acquired the lock, and so re-emptied the
queue.

%%%%%

\begin{figure}[bph]
\begin{scala}
import scala.collection.mutable.Queue

class MonitorPartialQueue[T] extends PartialQueue[T]{
  /** The queue itself. */
  private val queue = new Queue[T]

  /** A monitor object, to control the synchronisations. */
  private val lock = new Lock

  /** Condition for signalling that the queue is not empty. */
  private val notEmpty = lock.newCondition

  /** Enqueue £x£. */
  def enqueue(x: T) = lock.mutex{
    queue.enqueue(x)
    notEmpty.signal() // Signal to a waiting dequeue.
  } 

  /** Dequeue a value.  Blocks until the queue is non£-£empty. */
  def dequeue(): T = lock.mutex{
    while(queue.isEmpty) notEmpty.await() // Wait for a signal.
    queue.dequeue()
  }
}
\end{scala}

The term \emph{monitor}\index{monitor} is often used to describe a concurrent
object, encapsulating data and operations on that data, providing mutually
exclusive access to the data, together with a wait/signal mechanism.  We will
see another implementation of monitors, provided by the Java Virtual Machine,
in Chapter~\ref{chap:JVMMonitors}, and a further implementation, using
semaphores, in Chapter~\ref{chap:semaphores}.

It is very common for a thread to have to wait until some property becomes
true.  SCL |Conditions| include an operation |await(test)|\SCLIndex{await}
that waits until |test| becomes true.  It is defined as follows:
%
\begin{scala}
  def await(test: => Boolean): Unit = while(!test) await()
\end{scala}
%
Remember that the type signature ``|test: => Boolean|'' means that |test| is a
computation that is passed by name.  It is evaluated only in the body of the
operation, on each iteration of the loop.

Thus the |dequeue| operation could be written more succinctly as:
\begin{scala}
  def dequeue(): T = lock.mutex{
    notEmpty.await(queue.nonEmpty) // Wait for a signal.
    queue.dequeue()
  }
\end{scala}

It is tempting to write the |enqueue| operation as follows, so that only an
|enqueue| that makes the queue nonempty signals.
%
\begin{scala}
  def enqueue(x: T) = lock.mutex{ // £\emph{This doesn't work!}£
    queue.enqueue(x)
    if(queue.length == 1) notEmpty.signal() // Signal to a waiting dequeue.
  } 
\end{scala}
%
However, this doesn't work.  Suppose the queue is empty, and there are two
waiting |dequeue|s.  Now if an |enqueue| runs it will signal to one of them.
However, it is possible that a second |enqueue| obtains the lock before the
|dequeue| that received the signal.  With the above implementation, the second
|enqueue| will not signal.  That means that only one of the |dequeues|
receives a signal and runs, and the second it left waiting, despite the fact
that there is a second value in the queue that it could take. 


Try to choose good names for |Condition|s.  I use the convention that the name
of a |Condition| corresponds to the property that a signal on the condition
indicates, or, equivalently, the property for which a thread waits.  Above, a
signal on |notEmpty| indicates that the queue is not empty; and a |dequeue|
waits on |notEmpty| until the queue is not empty.


%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The above partial queue implementation uses a single |Condition|.  However, a
monitor may use multiple |Condition|s.

%%%%%

\begin{figure}
\begin{scala}
class BoundedMonitorPartialQueue[T](bound: Int) extends PartialQueue[T]{
  /** The queue itself. */
  private val queue = new Queue[T]

  /** A monitor object, to control the synchronisations. */
  private val lock = new Lock

  /** Condition for signalling that the queue is not full. */
  private val notFull = lock.newCondition

  /** Condition for signalling that the queue is not empty. */
  private val notEmpty = lock.newCondition

  /** Enqueue £x£.  Blocks while the queue is full. */
  def enqueue(x: T) = lock.mutex{
    notFull.await(queue.length < bound) // Wait for a space (1).
    queue.enqueue(x)
    notEmpty.signal() // Signal to a waiting dequeue at (2).
  }

  /** Dequeue a value.  Blocks until the queue is nonempty. */
  def dequeue(): T = lock.mutex{
    notEmpty.await(queue.nonEmpty) // Wait for a signal (2).
    val result = queue.dequeue()
    notFull.signal() // Signal to a waiting enqueue at (1).
    result
  }
}
\end{scala}
\caption{A bounded partial queue implemented using {\scalastyle Condition}s.}
\label{fig:BoundedMonitorPartialQueue}
\end{figure}

Figure~\ref{fig:BoundedMonitorPartialQueue} gives an implementation of a
\emph{bounded} partial queue that can hold at most |bound| values.  Thus an
|enqueue| might have to wait for there to be a space for its value.  This is
implemented using a second |Condition|, |notFull|.  A |dequeue| signals on
this condition when it removes a value, to signal that the queue is not full.

Study the details of the implementation.
\end{instruction}

We could have written the |dequeue| operation as
%
\begin{scala}
  def dequeue(): T = lock.mutex{
    notEmpty.await(queue.nonEmpty); notFull.signal(); queue.dequeue()
  }
\end{scala}
%
The thread continues to hold the lock after signalling, so it is fine to
signal before dequeueing.  However, the order in
Figure~\ref{fig:BoundedMonitorPartialQueue} seems more logical.

When there are multiple signals in a monitor, it is helpful to make clear
where a particular signal will be received.  In
Figure~\ref{fig:BoundedMonitorPartialQueue}, I have labelled the two |await|s
and |signal|s~``(1)'' and~``(2)'', to help the reader tie them together. 

We can adapt the linearizability tester to test this bounded queue.  The
enqueue operation on the sequential specification datatype needs to be adapted
to capture the operation's precondition, as follows:
%
%\begin{mysamepage}
\begin{scala}
  def seqEnqueue(x: Int)(q: SeqQueue) : (Unit, SeqQueue) = {
    require(q.length < bound); ((), q.enqueue(x))
  }
\end{scala}
%\end{mysamepage}
%
When testing the implementation, we should pick a fairly small value for
|bound| (on, at least, a good proportion of the runs).  This makes it likely
that the queue sometimes becomes full, and so ensures that the testing covers
this case.
