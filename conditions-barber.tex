\section{Example: The Sleeping Barber}

Different concurrent programs produce different synchronisation problems.
Often these are presented in terms of colourful real-life scenarios.  One such
example is the sleeping barber.

A small barbershop is run by a single barber, and has several chairs.  When
there are no customers, the barber sleeps in his chair.  When a customer
arrives and finds the barber sleeping, he wakes up the barber, sits in the
chair, and sleeps while the barber cuts his hair.  If another customer arrives
in the meantime, he sleeps in one of the other chairs.  When the barber
finishes the haircut, he wakes up the customer, holds the door open, and waits
for him to leave.  If there are waiting customers, he wakes one up and waits
for him to sit in the chair; otherwise, he goes back to sleep.

%%%%%


We will implement a synchronisation object to solve this synchronization
problem.  The synchronisation object will extend the trait in
Figure~\ref{fig:BarberT}, with the following operations:
%
\begin{description}
\item[\scalastyle getNextCustomer]
The barber wakes up a customer and waits for him to sit in the chair, or
sleeps until a customer arrives;

\item[\scalastyle getHaircut]
A customer arrives and waits until the barber is ready, then sits in the
chair;

\item[\scalastyle finishedCut]
The barber wakes up the customer, and waits for him to leave;

\item[\scalastyle waitForHaircut]
The customer waits for the barber to finish, then leaves.
\end{description}
%
Each pair of operations will involve a signal in each direction between the two
parties.

\begin{figure}
\begin{scala}
trait BarberT{
  def getHaircut(): Unit
  def getNextCustomer(): Unit
  def waitForHaircut(): Unit
  def finishedCut(): Unit
}
\end{scala}
\caption{Trait for the sleeping barber synchronisation object.}
\label{fig:BarberT}
\end{figure}


Figure~\ref{fig:sleeping-barber-threads} gives  barber and customer threads
that could be used in a simulation of the sleeping barber example.

%%%%%%

\begin{figure}
\begin{scala}
  val barber: BarberT = ...

  def barber = thread("Barber"){
    while(true){
      sleep(Random.nextInt(500)); println("Barber ready")
      barber.getNextCustomer; println("Barber cutting hair")
      sleep(Random.nextInt(500)+1000); println("Barber finished")
      barber.finishedCut
  } }

  def customer(me: Int) = thread("Customer"+me){
    while(true){
      sleep(Random.nextInt(6000)); println("Customer "+me+" arrived")
      barber.getHaircut; println("Customer "+me+" getting haircut")
      barber.waitForHaircut; println("Customer "+me+" finished haircut")
  } }
\end{scala}
\caption{Threads for simulating the sleeping barber example.}
\label{fig:sleeping-barber-threads}
\end{figure}

%%%%%

One way to approach the design of the |BarberT| object is to realise that each
iteration involves two independent synchronisations.  We can treat these
separately, with a different synchronisation object for each.  In fact, we can
capture each synchronisation as an instance of the same synchronisation
pattern.  Suppose we have multiple threads of type~$A$, and a single thread of
type~$B$: we can design a synchronisation object to allow an $A$-thread to
synchronise with the $B$-thread.  In each synchronisation of the sleeping
barber problem, we can take type~$A$ to be the customers, and type~$B$ to be
the barber.

Figure~\ref{fig:barber-Sync} gives such a synchronisation object.  This uses a
pair of conditions for signalling in each direction.  Initially, the
$A$-thread waits to receive a signal on |bReadyC|.  In addition, we use a
boolean variable |bReady| to record whether the $B$-thread has signalled: this
is necessary for the case that the $B$-thread signals before an $A$-thread is
waiting.  The $A$-thread needs to recheck |bReady| when it receives a signal,
in case another $A$-thread has run in the meantime.  Subsequently, the
$B$-thread waits to receive a signal back from the $A$-thread on |aReadyC|.
There is no need for an additional boolean variable at this point, because the
$A$-thread cannot signal before the $B$-thread releases the lock, and only a
single $A$-thread can progress past the first signal at a time.  

%%%%%

\begin{figure}
\begin{scala}
class Sync{
  /** Is the £$B$£ thread ready to synchronise? */
  private var bReady = false

  /** Lock to provide mutual exclusion. */
  private val lock = new Lock

  /** Condition to signal that an £$A$£ thread is ready. */
  private val aReadyC = lock.newCondition

  /** Condition to signal that the £$B$£ thread is ready. */
  private val bReadyC = lock.newCondition

  /** Operation for a thread of type £$A$£ to synchronise. */
  def syncA() = lock.mutex{
    bReadyC.await(bReady)  // Wait for £$B$£ (1).
    bReady = false // Consume signal.
    aReadyC.signal() // Signal to £$B$£ at (2).
  }

  /** Operation for a thread of type £$B$£ to synchronise. */
  def syncB() = lock.mutex{
    bReady = true; bReadyC.signal() // Signal to £$A$£ at (1).
    aReadyC.await() // Wait for £$A$£ (2).
  }
}
\end{scala}
\caption{Class to mediate synchronisations between threads of type $A$ and a
  single thread of type~$B$.}
\label{fig:barber-Sync}
\end{figure}

%%%%%

\begin{instruction}
Make sure you understand the implementation of the synchronisation object.
\end{instruction}

The class |Sync| can be tested by running suitable threads that call the
operations and write into a log before and after each.  We can then traverse
the log and check that the number of times |sync1| returns does not exceed the
number of times that |sync2| is called, and vice versa.

Figure~\ref{fig:Barber2} then gives a straightforward implementation of the
main synchronisation object that encapsulates two |Sync| objects.  Each
operation simple calls the relevant operation on a |Sync| object.

%%%%%

\begin{figure}
\begin{scala}
object Barber2 extends BarberT{
  /** Synchronisation object for the £getHaircut£/£getNextCustomer£
    * synchronisation. */
  private val sync1 = new Sync
  /** Synchronisation object for the £waitForHaircut£/£finishedCut£
    * synchronisation. */
  private val sync2 = new Sync

  def getHaircut() = sync1.syncA()
  def getNextCustomer() = sync1.syncB()
  def waitForHaircut() = sync2.syncA()
  def finishedCut() = sync2.syncB()
}
\end{scala}
\caption{An implementation of the main synchronisation object for the sleeping
  barber example, encapsulating two {\scalastyle Sync} objects.}
\label{fig:Barber2}
\end{figure}

%%%%%

In fact, we could have used a slightly simpler synchronisation object for the
second synchronisation, between |waitForHaircut| and |finishedCut|.  At most a
single customer at a time can be at this point.  That means that we could
replace 
\begin{scala}
  bReadyC.await(bReady)
\end{scala}
in |syncA| with
\begin{scala}
  if(!bReady) bReadyC.await(); assert(bReady)
\end{scala}
(where the assertion could be considered optional), because no other customer
could have set |bReady| to |false| in the meantime.  It's not clear that this
is worth the bother.


%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%


Synchronisation problems like this can be difficult.  In order to come up with
a correct and understandable design, it is useful to use state variables that
indicate which processes are in different states.  In the |Sync| objects, the
variable |bReady| indicates that a $B$-thread is waiting for a signal.  In
other synchronisation problems, it can be useful to keep track of how many
processes are in particular states.  
%
To track down bugs, it can be useful to write plenty of assertions: if nothing
else, these act as good documentation; and they might reveal a mistake.  If
all else fails, it can help to use logging, particularly of the sending and
receiving of signals.
